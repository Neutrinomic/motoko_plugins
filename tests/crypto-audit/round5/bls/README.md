# BLS round-five protocol audit

No production defect was found. This change adds tests only; public types,
compiler implementation, runtime implementation and ABI are unchanged. Central
source-pin rebuilding reproduced the byte-identical BLS runtime.

Review covered the public module, compiler schema/generator/reference, canonical
group decoding, raw and prepared verification, aggregation, proof reuse, scalar
and batch validation, and the vendored prepared/streaming pairing interfaces.
An independent reader checked both these paths and the new test expectations.
Earlier round-three/four audits already cover malformed encodings, subgroups,
infinity, sorting/cache/cap boundaries, MSM, streaming identity masks and guarded
native buffers; those archived corpora were inspected to avoid duplicating them.

The new maintained suite covers:

- IC G1 NUL versus POP/AUG signatures, with binary message bytes and exact
  caller-supplied `ic-state-root` framing.
- Ethereum G2 POP versus NUL/AUG signatures, and PoP versus a signature on the
  same public-key bytes. A false proof cannot produce a prepared PoP key.
- Direct/prepared singles and every direct/prepared aggregate entry point.
  Two separately prepared handles for the same canonical key exercise IC key
  grouping and repeated Ethereum keys/messages.
- Exact independent G1/G2 hash outputs at DST lengths 255 and 256.
- Maintained compiler rejection of Blob-to-IC-handle forgery and use of a plain
  Ethereum prepared key where a PoP key is required. These trust-boundary checks
  previously lived only in the manually invoked prepared audit archive.

`generate.py` pins py_ecc 8.0.0 and generates 23 small byte fixtures using only
the test scalar 5. Ethereum fixtures use py_ecc's signature-scheme APIs; IC
fixtures use its G1 hash, multiplication and compression APIs. No output is
generated by the plugin. The 256-byte DST normalization follows
[RFC 9380 section 5.3.3](https://www.rfc-editor.org/rfc/rfc9380.html#section-5.3.3).
Ciphersuite and proof domain choices follow
[BLS signature draft section 4.2](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-bls-signature-06#section-4.2).
The IC framing expectation follows the plugin's documented raw-byte contract.

`vectors.tsv` is the native fixture source; `ProtocolVectors.mo` is generated
from the same data. The public suite is shared by `crypto-bls-protocol.mo` and
four `BLS12381Protocol.ash.json` methods. Both are discovered by the existing
shared runners. Four native tests are registered in the existing runtime crate.
Their helpers check immutable inputs, unaligned buffers/descriptors, output
guards, untouched output on errors and canonical Boolean success bytes.

Regenerate/check fixtures using Python with py_ecc 8.0.0 installed:

```sh
python3 tests/crypto-audit/round5/bls/generate.py --check
```

From the frozen compiler's Nix environment, with the plugins checkout as
`$lane`, matching `dist/bls12-381`, and the compiler `bin/` first on `PATH`:

```sh
cargo test --manifest-path "$lane/Cargo.toml" -p motoko-compute-bls12-381 \
  --locked --offline --release --target-dir "$lane/_build/round5-bls/target" round5
test-runner -b -j2 "$lane/packages/fast/tests/run/crypto-bls-protocol.mo" \
  "$lane/packages/fast/tests/fail/crypto-bls-prepared-blob-forge.mo" \
  "$lane/packages/fast/tests/fail/crypto-bls-prepared-pop-required.mo"
```

Execution results and hashes are recorded in `report.json`: four native tests,
three public/fail fixtures and all four central Ash methods passed. Central
`PreparedComposition` also passed its shared actual-GC test, including BLS IC
prepared-key verification after confirmed collection and collection after
references are released. This does not establish exact live memory or erasure.
Full arithmetic corpora, full-stack limits and side-channel behavior remain
outside this focused suite. Earlier evidence is not reported as a fresh run.
