# P256 test coverage

The 19 Ash methods import `mo:fast/P256` and load only the `p256` plugin.
SHA-256 message digests are committed independent values, so the suite does not
implicitly rely on the SHA256 plugin. Core supplies ordinary Blob/Array helpers.
The checked-in Ash configuration enables `--force-gc` and `--sanity-checks`.

Sources are [RFC 6979 section A.2.5](https://www.rfc-editor.org/rfc/rfc6979.html#appendix-A.2.5)
and [C2SP Wycheproof at commit `878e5366008753df2064d40c49f8e2f50f9c6af7`](https://github.com/C2SP/wycheproof/blob/878e5366008753df2064d40c49f8e2f50f9c6af7/testvectors_v1/ecdsa_secp256r1_sha256_test.json).
The full 484-case corpus and its Apache 2.0 license are vendored under
`plugins/p256/tests/vectors/`. `selected-wycheproof-ids.json` records the exact
65 cases executed through the public Motoko API. Message prehashes were computed
with Python `hashlib.sha256(bytes.fromhex(msg)).digest()` independently of the
plugin. Expected compact bytes come from strict DER integer decoding, not from
the implementation under test. The Rust runtime suite executes all 484 cases.

Digest boundary expectations come from
`plugins/p256/tests/vectors/rfc6979-digest-boundaries.json`, with a reproducible
Python generator alongside it. Python HMAC and integer arithmetic implement
RFC6979 nonce generation and the ECDSA scalar equation; OpenSSL independently
derives the nonce point. OpenSSL's separate deterministic ECDSA implementation
must agree byte-for-byte, and both published RFC sample/test vectors are checked
first. The generator uses `cryptography==46.0.3` (OpenSSL 3.5.4).

[RFC6979 section 2.3.4](https://www.rfc-editor.org/rfc/rfc6979.html#section-2.3.4)
defines `bits2octets`, which reduces a 256-bit P-256 hash modulo the group order;
[section 3.2](https://www.rfc-editor.org/rfc/rfc6979.html#section-3.2) uses this
conversion when seeding the nonce generator. Merely checking that a signature
verifies cannot detect omission of this reduction: both signatures can verify
while only one follows RFC6979. The explicit boundary answers cover that gap.

`packages/fast/tests/run/crypto-p256.mo` separately covers the RFC signatures,
high-S verification, normalization, encoding and typed failures through the
interpreter and Wasm test runner with sanity checks enabled. It includes all
four exact digest boundary signatures as well. Prepared verification checks the
same independent answers, aliases and record/array storage, malformed preparation,
wrong digest/key and validation precedence. The
`tests/fail/crypto-p256-prepared-*` cases require rejection of Blob-to-handle
forgery, handle-to-Blob projection, Candid encoding, stable storage, shared method
arguments and `debug_show`. Tests inspect preparation errors with pattern matching;
they never use equality to inspect opaque handles.

`tests/run/crypto-p256-projective-check.mo` repeats the four projective boundary
cases through the interpreter and Wasm runner. Their exact public keys, digests,
compact signatures and expected verdicts come from
`benchmarks/crypto/round4/p256/projective-check/vectors.json` (SHA-256
`d1e2824284d92f29cb86346b9059d1eabae67bffeb1349b2be775504befa1a62`).
Its separate Python generator constructs Q = r⁻¹R with digest zero and s = 1,
checks curve membership and subgroup order, and verifies the resulting equation
using ordinary affine arithmetic. The two invalid signatures have valid scalar
and point encodings, so both APIs must return `#ok(false)` rather than a parsing
error. The field modulus p and group order n are distinct boundaries.

All Ash methods are update calls to leave room for elliptic-curve arithmetic.
Each Wycheproof method contains at most 13 vectors. Ash metrics include test
setup, conversions and assertions; they are correctness evidence rather than
isolated performance measurements. The alias/retention test is not a proof of
GC reclamation or constant-time execution. The separate DER72 GC test observes
reclamation while preserving one managed output, but does not prove arbitrary
GC schedules or reclamation of every plugin object. The suite does not simulate
upgrades or interrupted calls.

The DER72 test allocates 72 MiB of disposable arrays in nine batches. The SDK's
incremental collector uses 64-MiB partitions and excludes the active allocation
partition from evacuation; crossing that boundary is necessary to exercise
collection of the partition containing the saved output. Pressure data is not
retained. Nine allocation continuations and four settling continuations check
the saved Blob, its aliases and its exact compact decoding throughout. The
test's returned metrics measure only its final validation closure, excluding
the allocation pressure and asynchronous collection phases.

The prepared-key GC test uses the same nine-batch pressure pattern and four
settling continuations, first while the key is retained and again after every
saved handle root has been dropped. Each phase requires over 4 MiB of observed
reclamation. The second phase confirms collection after releasing the roots;
aggregate reclaimed bytes do not identify individual prepared allocations or
prove their exact retained size. Its final metrics measure only re-preparation
and verification, excluding both pressure phases. No handle representation is
exposed or compared, so the interpreter and Wasm may use different private bytes.

## Validation

The new round-4 projective boundary tests are authored but not yet executed.
The prior 18-method evidence below remains unchanged and does not validate this
additional method or the round-4 runtime.

On 2026-10-13, the selected width-8 prepared implementation passed all **18 Ash
methods**, the public run test through the interpreter, both IR interpreters and
Wasm, and all six reviewed negative type tests. Ash enabled `--force-gc` and
`--sanity-checks`. Both reclamation assertions in the prepared-key GC test passed,
as did subsequent re-preparation and verification. The largest correctness batch
used approximately 417 million instructions. These batch metrics include fixture
setup and assertions, so they are not prepared-verification microbenchmarks.

[P256-prepared-validation.json](P256-prepared-validation.json) preserves the
complete logs, source/tool/artifact hashes, generated canister hash and isolated
test commands. The SDK was source revision
`9f6ebeedc547e389a0529b4c91442e46b88fcbe0`, with compiler SHA-256
`24d8d0b951c4d2928c505ed6e91503750c83cf754d9518dcda9a265a8842beb2`.
The selected runtime SHA-256 was
`0d2fa29baa9ab136ba5bd8a0cb55da5478ff6459fe1e8c02fecdc3e25dde3972`.
A private copy of Ash selected that SDK's compiler wrapper and RTS files;
no global compiler or home environment was changed.

On 2026-10-12, all **15 Ash methods passed** on PocketIC using the source Ash
checkout at `/srv/shared/code/ash` and the private round-2 candidate
`_build/crypto-optimization-round2/p256-combined`, built against Motoko
`2.0.0-14-g92b1bdecb`. The isolated Ash configuration pointed at this candidate's
source and artifacts and enabled `--force-gc --sanity-checks`, matching the
checked-in configuration. No methods failed or skipped. The largest correctness
batch used approximately 147 million instructions. The DER72 retention test
passed its assertion that more than 4 MiB had been reclaimed while the saved
output remained intact.
